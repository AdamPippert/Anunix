# Day 044: Select validated routing profiles within a finite envelope

The August 8 briefing separates offline profile synthesis from deterministic runtime selection and enforcement.
The comparison baseline, `4447733`, provides build markers, routing trials, fixed harness receipts, and typed policy tasks.
Its direct tuning path changes global weights without a request-specific profile envelope.

The baseline regression exposes the unconditional global activation path.

## Implementation

The [profile compiler](../../kernel/core/route/profile.c) accepts bounded weights and one to eight distinct request cases from the trusted controller.
A case specifies routing strategy, locality, network permission, remote-model permission, and an optional topology range.
The compiler captures the incumbent weights and generation, compiled kernel marker, engine snapshot, and scheduler queue depths.
It supports at most eight engines, matching the live route planner's candidate capacity.

For each case, the compiler simulates both the incumbent and proposed weights against the same frozen environment.
Both simulations must find a feasible candidate and choose the same winner.
The proposal must preserve the incumbent's runner-up margin when that margin exists.
The compiler rejects malformed cases, duplicate cases, changed environments, and an incumbent with an active tuning trial.

A successful compilation seals the profile, cases, engine environment, and per-case results into a structured state object.
The compiler retains a private issuance record containing that object's identifier and payload digest.
There are 32 simultaneous issuance slots.
A copied object or edited payload cannot acquire the original issuance record.

Cells can name a profile through their routing policy.
The [live planner](../../kernel/core/route/planner.c) starts each decision with a snapshot of the incumbent weights.
It selects the requested profile only after validating issuance, read access, payload integrity, kernel marker, incumbent generation, and a matching request case.
It also requires the captured engine fields and scheduler queue depths to match the current Resource Twin.

Successful selection changes the copied weights for that routing decision.
It does not activate a global tuning trial or replace the system's incumbent.
Every profile rejection leaves the planner using the incumbent and records the rejection status in the route result.
The existing engine feasibility checks still run before scoring and selection.

The controller can revoke issuance while preserving the sealed object for audit.
Runtime selection rechecks the issuance record before returning the profile weights.
An active cell can use an issued profile, but cannot compile or revoke profiles.

The [native regression](../../kernel/core/tools/research_day044.c) compiles a profile for a local-first request against the registered engine environment.
It changes the request strategy and verifies incumbent scoring with `ANX_EBUSY` recorded for the profile.
Restoring the validated request enables profile scoring without changing the global incumbent.

The fixture also tests a forged sealed copy, payload corruption, withdrawn read permission, and an engine-quality change.
An intervening global tuning trial invalidates the profile generation even after rollback restores the same weight values.
A freshly compiled profile works during actual cell execution, where compilation and revocation remain forbidden.
Revoking that profile makes the live planner return to incumbent scoring.

## Limits

The validated envelope is a finite set of exact routing cases and one captured engine and queue environment.
The selector does not interpolate between cases or infer that nearby hardware or workloads are equivalent.
A changing queue can conservatively trigger fallback even when the same policy would remain useful.

The compiler checks winner and margin preservation in the Resource Twin's deterministic scoring model.
It does not establish improved latency, energy, task quality, or throughput.
The Twin excludes the existing bounded JEPA score contribution; this step does not certify that predictor's behavior.

Linux Kconfig synthesis and portfolios of specialized kernels remain outside this step.
It does not train an optimizer, emit arbitrary configuration code, rebuild kernels at runtime, or change CPU scheduling classes.
The profile stores the kernel marker and retains private issuance only for the current kernel lifetime.
It cannot be reactivated after reboot solely by copying its sealed object.

Snapshot capture and engine enumeration retain the existing registry's concurrency limitations.
Validation does not lock the entire machine between its environment check and route execution.
The tests establish profile admission, fallback, and scoring behavior without a workload-performance claim.
