# Day 017: Govern context metadata projections

The July 12 briefing separates stored information from information a model is eligible to consume.
Its Context MMU proposal combines access, trust, versions, and residency.
Anunix already has object access policies and an ICM metadata catalog.
The comparison baseline, `becb198`, lets ICM read and change annotations through raw object lookup without evaluating those policies.

## Implementation

ICM views require the active caller's `READ_META` permission.
Denied reads preserve the caller's previous output buffer.
Catalogs, counts, and published views omit objects whose metadata the caller cannot read.
Only active or sealed objects qualify for these views.

Tagging and publication markers require `WRITE_META` permission before any annotation changes.
Authorized annotations remain editable on sealed objects because metadata permission is separate from payload mutation.
The authority annotation remains descriptive text and cannot change the object's access policy or the consumer's role.

All direct ICM lookups now release their object references on success and failure.
Views initialize their complete output structure before copying permitted metadata.
Annotation writes return the first storage error instead of reporting unconditional success.

The [native regression](../../kernel/core/tools/research_day017.c) creates protected and public artifacts with separate owner and caller cells.
The other caller cannot read, catalog, tag, or publish the protected artifact.
Changing the public artifact's authority annotation does not grant access to the protected artifact's metadata or payload.
The owner retains access and can update permitted annotations on the sealed artifact.
The fixture also checks unchanged policy and reference counts after repeated catalog operations.

## Limits

This change protects metadata projection; it does not introduce a complete model-context lease, trust classifier, or supersession resolver.
An object without a matching access rule permits access by default.
Consumers must not interpret an authority annotation as an access grant.
Trusted kernel code can still access raw object and metadata structures.

Multiple annotation updates are not transactional; an allocation failure can leave earlier authorized updates in place.
The checks follow the current synchronous kernel execution model and do not provide concurrent policy snapshots.
