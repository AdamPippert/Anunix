# Day 050: Reclaim pages behind stable logical views

The August 14 briefing separates logical liveness from the physical unit of allocation.
Anunix already tracks object retention and workflow dependencies, but those mechanisms do not repack live bytes within physical pages.
The comparison baseline, `f228dae`, lacks a handle-based storage layer that can relocate immutable records while preserving surviving references.

## Scope

The source is [Day 050 in the daily review](daily-review.md#day-050--2026-08-14).
The source message identifier is `880a7069-0965-4314-9d09-048664fc8ba6`.
This step implements bounded resource views over native CPU pages.
The baseline fixture first introduces logical handles without compaction, then demonstrates that released records still occupy physical pages.
The experiment does not implement the source's GPU KV-cache algorithm.

## Implementation

The [resource-view API](../../kernel/include/anx/resource_view.h) separates logical record identity, alias handles, and physical page placement.
A controller creates a pool for an existing Cell and selects a capacity from one through 32 pages.
Each page contains 4,096 bytes; the maximum primary storage is 128 KiB per pool.
The registry supports 16 pools, 64 records per pool, and 128 aliases per pool.
Each immutable record contains one through 4,096 bytes and can span page boundaries.

The [storage manager](../../kernel/core/mem/resource_view.c) stores private mappings and a SHA-256 digest for each record.
The API returns copied bytes and logical metadata, without exposing physical pointers.
Reads check the complete record digest before copying any requested bytes.
Invalid ranges or corrupted contents leave the destination buffer unchanged.

The owner or controller can insert records, clone aliases, read records, and release aliases.
Only the controller can create or destroy pools and invoke physical compaction.
A pool retains its owner's Cell reference until destruction.
Destruction fails while any alias remains live.
Terminal owners permit inspection and cleanup, but cannot acquire new records or aliases.

Releasing an alias removes that handle immediately.
The last alias release makes its record logically dead while preserving the current page allocation.
Identifiers never repeat within the boot, so slot reuse cannot revive released handles.
A surviving alias keeps its record live, including after the original handle is released.

Compaction requires a caller-selected minimum dead-byte threshold and temporary-page budget.
The manager calculates the pages needed for all live bytes and rejects plans that cannot strictly reduce the current page count.
Insufficient temporary capacity returns `ANX_ENOMEM`; an unmet threshold or nonshrinking plan returns `ANX_EBUSY`.
An empty pool can reclaim all pages with zero temporary pages.

The manager allocates fresh destination pages and copies each live record into packed storage.
Every copied record must match its original digest before the mappings change.
Allocation failure or a digest mismatch frees temporary pages and preserves the old mappings.
Readers, alias operations, and compaction share a lock, so no reader observes partial relocation.
After successful checks, the manager updates offsets and returns the old pages to the physical allocator.
Freed pages are cleared before release.

## Native checks

The [regression](../../kernel/core/tools/research_day050.c) fills three pages with eight records of 1,536 bytes each.
It retains two records, including one through a cloned alias, and releases the other records.
Compaction uses one temporary page and reduces primary allocation from three pages to one.
The test checks that the allocator gains two free pages and both surviving records retain their identities and exact bytes.

The regression also checks threshold rejection, temporary-capacity rejection, full alias capacity, and stale handles after slot reuse.
A test-only corruption control verifies unchanged mappings, buffers, and free-page counts after a rejected copy.
An actual foreign Cell fails read, release, insertion, and management calls.
The owning Cell can clone and read an alias but cannot compact the pool.
Final cleanup reclaims every data page with zero temporary pages.

## Limits

The pool's byte and page bounds are independent of the memory-admission ledger and engine leases.
The controller must account for pool capacity and temporary headroom when selecting system-wide resource budgets.
The page statistics exclude registry metadata, allocator metadata, and stack storage.
The existing physical allocator's concurrency limits still apply outside the resource-view lock.

Records are immutable opaque bytes, without automatic State Object permissions, provenance, workflow dependencies, or model semantics.
Callers express liveness through explicit alias ownership and release.
The implementation supplies no raw shared mappings, GPU integration, persistent recovery, compression, or automatic pressure detector.
Compaction runs synchronously under the registry lock; latency and contention remain unmeasured.
The source's throughput and capacity improvements remain untested beyond this deterministic fragmentation fixture.
