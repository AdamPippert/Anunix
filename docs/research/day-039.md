# Day 039: Restore a suspended workflow from an exact checkpoint

The August 3 briefing describes an agent continuation as a graph of versioned representations.
The comparison baseline, `c1a6f02`, preserves workflow progress in a heap allocation and serializes graph descriptions as text.
The baseline cannot restore executor progress from a state object after unloading that allocation.

## Scope

The source is [Day 039 in the daily review](daily-review.md#day-039--2026-08-03).
The source message identifier is `583e07ee-0781-4425-81ed-0a3a942cebd5`.
The briefing recommends exact state transitions with dependency checks and explicit restoration contracts.
This step applies that pattern to suspended workflow execution.
The baseline adapter stores graph text but exposes no executor restoration operation.

## Implementation

The [checkpoint module](../../kernel/core/workflow/checkpoint.c) captures a suspended workflow into a sealed state object.
The image contains completed-node flags, remaining dependencies, intermediate object identifiers, trace entries, outputs, and the recorded concurrency cap.
It also records the workflow identity, run timestamp, topology revision, image revision, and graph and policy digest.
The controller must call save and restore outside an active cell.

Save records at most 128 distinct dependencies, including intermediate objects, state references, outputs, and cell trace objects.
Each dependency has a one MiB payload limit for hashing.
The image records each dependency's identifier, version, type, sensitivity, and payload digest.
The checkpoint inherits the highest dependency sensitivity.
An unresolved staged mutation rejects capture without unloading progress.

After successful object creation and sealing, save records the issued identifier and digest in the workflow registry.
Save then releases the temporary continuation and trace arrays.
The workflow remains suspended, and its existing intermediate liveness records remain active.
A failure before sealing leaves the original progress available.

Restore accepts only the latest issued checkpoint for that workflow and run.
It checks the sealed payload against the recorded digest and current graph before allocating replacement progress.
It then checks every dependency's current read access, version, type, sensitivity, and payload hash.
The Day 038 reuse guard also runs before restoration succeeds.

Successful restore consumes the checkpoint, preventing another restore of the same progress.
Starting or resuming execution also consumes any previous checkpoint.
The executor rejects a fresh start for suspended and human-review workflows, so callers cannot bypass continuation handling through restart.
An unloaded checkpoint can still be aborted without restoring its dependencies.
The Day 005 fixture now explicitly aborts each suspended trial before starting its next independent promotion trial.

The [native regression](../../kernel/core/tools/research_day039.c) executes an editor operation that creates a result object containing `42`.
A denied promotion node then suspends the graph.
The fixture saves, unloads, restores, and resumes through the existing executor.
The completed editor node retains its original result identifier and appears once in the final trace.

The fixture also checks repeated restore, an unissued identifier, graph drift, staged dependency changes, and withdrawn read access.
Rejected restores leave the continuation unloaded and available for a later valid restore.
The test aborts its staged edit before restoring the original dependency state.

## Limits

This image preserves workflow executor state in the current object store and registry lifetime.
It does not restore an entire host after reboot or migrate a workflow into a different registry.
The format uses native structures and has no cross-version or cross-architecture compatibility contract.

The checkpoint contains dependency identities and digests, not full copies of model weights, KV caches, tokenizer state, or tool environments.
Restore requires those dependencies to remain available and unchanged.
Dependency checks do not hold every object lock throughout subsequent execution.
The existing registry and object pointers remain accessible to kernel code.

The completed operation in the test creates a local result object.
The test does not establish exactly-once network delivery, external effect recovery after a crash, or durable effect settlement.
The tests establish bounded progress restoration without a latency or memory-reclamation claim.
