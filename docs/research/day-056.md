# Day 056: Model restoration capacity in a frozen Resource Twin

The August 20 briefing proposes bounded resource simulation before live scheduling changes.
It distinguishes retained data from the local working capacity required to reactivate that data.
Anunix already snapshots engines and queue depths, but the comparison baseline, `8c237cb`, does not include reservation capacity in restoration planning.

## Scope

The source is [Day 056 in the daily review](daily-review.md#day-056--2026-08-20).
The source message identifier is `ddc17c69-af7e-4297-921f-6146b196222e`.
This step extends the native Resource Twin with frozen ledger capacity and a restoration feasibility check.
Its byte counts describe planning inputs and logical reservations; the fixture does not allocate or restore the declared retained dataset.

## Implementation

The [lease manager](../../kernel/core/route/lease.c) now captures total and available memory per tier, plus accelerator capacity, under its ledger lock.
The snapshot counts active root reservations once; child reservations remain covered by their parent.
Checked subtraction rejects an inconsistent ledger before changing the caller's output.
An uninitialized ledger reports unavailable capacity.

The [Resource Twin](../../kernel/core/twin/twin.c) retains that capacity snapshot alongside its existing engine and queue snapshots.
Ordinary routing simulation remains available when the lease ledger is unavailable.
Restoration planning instead returns `ANX_ENOTSUP` without capacity evidence.
Each subsystem snapshot is internally bounded; the combined Twin is not an atomic snapshot of the entire machine.

The [restoration request](../../kernel/include/anx/twin.h) declares a target memory tier, retained bytes, resident bytes, peak local restoration bytes, and extra accelerator demand.
Resident bytes must fit within retained bytes, and the restoration peak must cover the resident bytes.
The planner subtracts resident bytes from the peak to calculate the new memory capacity required.
This subtraction avoids counting an existing resident reservation twice.

The new demand must fit the snapshot's available memory and accelerator capacity.
An infeasible demand returns `ANX_ENOMEM` without publishing a result.
Malformed requests, inconsistent capacity totals, or invalid routing inputs return `ANX_EINVAL`.
A feasible request proceeds through the existing frozen routing simulation.
The planner never grants a lease, changes live weights, or reserves capacity.

## Native checks

The [regression](../../kernel/core/tools/research_day056.c) exercises these declared planning quantities:

| Quantity | Value |
| --- | ---: |
| Retained data | 64 GiB |
| Already reserved resident capacity | 64 MiB |
| Peak local restoration demand | 512 MiB |
| New memory capacity required | 448 MiB |
| New accelerator reservation | 20% |

The frozen routing winner and score match live deterministic routing in the tested configuration.
Changing the live engine's quality changes its live score while leaving the frozen simulation unchanged.
The current JEPA routing hook contributes no score adjustment in this configuration.

A competitor then leaves one byte less memory than restoration requires.
The old snapshot still predicts feasibility, while a fresh snapshot and an actual live lease grant both reject the demand.
A separate accelerator competitor produces the same live rejection.
After those competitors release their reservations, the live grant succeeds.

The regression also checks missing capacity evidence, inconsistent totals, invalid tiers and accelerator requests, malformed byte relationships, extreme demand, and an exact-capacity fit.
Rejected requests preserve the caller's output.
Final cleanup restores ledger availability and confirms that simulation did not change live routing weights.

## Limits

The caller supplies the resident count and peak estimate; the planner does not measure or verify a real restoration implementation.
Resident bytes must already be represented in the ledger for the subtraction to describe actual free capacity correctly.
The ledger's default capacities remain logical budgets rather than a measurement of free physical RAM or accelerator memory.
Retained bytes do not prove that an external store contains the required data.

A frozen snapshot provides advice and can become stale immediately.
The live admission path must recheck capacity before use.
An empty routing candidate set remains a valid simulation result, without authorizing execution.
The Twin still omits restoration bandwidth, dependency execution, crash recovery, learned uncertainty calibration, and physical data movement.
No source throughput, latency, prediction-error, or controller-overhead improvement was reproduced by this fixture.
