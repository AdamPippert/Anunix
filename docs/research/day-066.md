# Day 066: Preserve evidence behind a reusable procedure

The August 30 briefing separates raw execution evidence, compiled knowledge, and versioned procedural artifacts.
It emphasizes compatibility checks, independent validation, and preserved evidence before a learned procedure becomes executable.
At comparison baseline `a7d5c05`, Anunix has ICM annotations, workflow bundles, provenance, and verified inference receipts.
This step connects those ideas through a bounded native recipe with source evidence and a separate replay gate.

## Scope

The source is [Day 066 in the daily review](daily-review.md#day-066--2026-08-30).
The source message identifier is `dcdb3512-f8d3-4508-ba3b-f80e5a105b0f`.
The implemented recipe repeats one exact deterministic toy-model request.
Its knowledge object contains controller-supplied text describing the procedure.

The compiler packages that knowledge and verified execution evidence into a compact artifact.
It does not infer patterns from text, evolve Skills, or generate a procedure with a language model.
The narrow recipe makes compatibility and evidence checks executable in the native kernel.

## Implementation

The [procedure registry](../../kernel/core/workflow/procedure.c) holds at most 16 versioned handles.
Compilation requires a completed model-use record that performed computation, a sealed knowledge object, and the exact owner.
Reused results and requests with nonzero random seeds cannot supply the discovery evidence.
Only controller code can compile or validate a recipe.

The compiler reads the actual source result through the model-use API.
It preserves the receipt in a sealed execution-trace object linked to its model image and prompt.
The recipe records that evidence identifier, the request and source metadata, and the knowledge object's version and digest.
Its artifact links to the raw evidence and knowledge through the existing provenance graph.

The knowledge object contains 1–1024 bytes.
Both the recipe and its evidence use fixed native schemas and bounded payload sizes.
ICM classifies the artifact as a procedural recipe, while private registry state controls whether it can execute.
Changing catalog labels or a copied view cannot grant execution permission.

A new recipe starts as a draft.
Validation requires a different, later model-use record that completed a real computation.
That replay must match the owner, identity commitment, model image, prompt, versions, digests, output limit, and request digest.
Its output length and digest must match the discovery result.
The registry preserves the replay receipt in another sealed evidence object before marking the recipe validated.

| Preserved object | Role |
| --- | --- |
| Source receipt | Records the original computation and its exact sources. |
| Knowledge object | Holds the compact, supplied procedural description. |
| Recipe artifact | Binds the request, compatibility conditions, knowledge, and source evidence. |
| Validation receipt | Records the independent replay accepted for this artifact. |

Execution requires a fresh prepared model-use record belonging to the recipe's owner.
The recipe rechecks its artifact, knowledge, source evidence, replay evidence, and predecessor artifact before dispatch.
Each dependency check verifies sealing, type, schema, version, size, sensitivity, digest, and current owner access.
The supplied model request must match the validated recipe's compatibility conditions.

The Day 064 path performs the actual model computation and verifies the bytes consumed.
The recipe compares the resulting output with its accepted evidence and rechecks dependencies before returning it.
Loading or executing the artifact leaves the owner's network and remote-model permissions unchanged.

A new version can name a validated predecessor owned by the same Cell.
Its version number advances, and the predecessor handle remains retained while a descendant exists.
Each version requires its own replay validation.
An owner can explicitly select an earlier validated version with matching prepared inputs.
There is no automatic active-version pointer or inferred cross-model compatibility.

Removing a registry handle releases its owner reference.
The sealed artifact and evidence remain in the object store for inspection until explicitly removed through existing object controls.
Catalog metadata alone cannot recreate a removed execution grant.

## Native checks

The [regression](../../kernel/core/tools/research_day066.c) compiles a recipe from a real `AAAA` generation and a sealed knowledge description.
It rejects absent source records, unexecuted evidence, a foreign owner, and missing knowledge.
It changes a catalog label to claim validation and confirms that the draft still cannot execute.

The original computation cannot serve as its own independent replay.
An unexecuted request and a replay using the `BBBB` image also fail validation.
Deleting another draft's raw evidence prevents validation even when an otherwise matching replay exists.
The original source receipt remains sealed and inspectable after its model-use handle is released.

After a separate `AAAA` replay passes, the fixture changes each artifact dependency's version, bytes, and read permissions.
Every rejected execution preserves both the caller's output and its unconsumed model-use record.
A request for the incompatible `BBBB` image also remains unconsumed.
The matching request then executes and produces `AAAA`.

A second recipe version uses the `BBBB` image and requires its own successful replay.
The predecessor cannot be removed while that version exists.
Explicit selection of the earlier version still produces `AAAA`.
The owner then executes version two inside its Cell and receives `BBBB`; a foreign Cell cannot inspect or execute it.

## Limits

This implementation packages and validates an exact recipe for the existing toy CPU model.
It does not demonstrate model portability, generalized Skills, automatic knowledge distillation, or gains from accumulated experience.
The independent replay repeats the same prepared task; it is not a held-out benchmark or an estimate of reasoning quality.

The artifact schemas use the current native structure representation and do not define a portable import format.
The object store preserves sealed evidence, but registry handles and validation grants exist only during the current boot.
This step does not establish disk durability or recovery of execution grants after restart.

Earlier versions remain selectable when their own dependencies and permissions still hold.
That explicit selection does not automatically compensate external effects or roll back arbitrary application state.
The implementation does not reproduce the briefing's performance measurements or establish that a general experience compiler is necessary.
