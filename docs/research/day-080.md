# Day 080: Validate a group of staged objects before publication

The September 13 briefing treats speculative execution as a transaction with explicit commit and abort boundaries.
The source message is `8e6b3d50-036a-46c2-b5f4-8c5127cf88f1` in the [research conversation](https://chatgpt.com/c/6a3eabf4-cb88-83ea-942e-a601dd12b392).
The briefing separates reversible internal changes from external operations that require compensation or irreversible-effect admission.
The Anunix experiment extends the reversible object boundary to a bounded group of staged payloads.

## Comparison

| Area | Existing Anunix | Day 080 change |
| --- | --- | --- |
| Private mutation | Each State Object has one private payload stage | A batch names one through four distinct staged objects |
| Publication | Each commit validates and publishes one target | Every target passes validation before any payload changes |
| Abort | Each abort discards one private payload | Batch abort checks all owners before discarding any stage |
| Authority | Commit checks the original actor, ACL, identity, fence, and optional evidence review | Every target retains those checks inside the batch boundary |

The [Day 045 speculative candidate](day-045.md) predicts and checks one candidate before staging its result.
The [Day 072 evidence review](day-072.md) binds approvals to one proposed payload.
Neither API previously provided a commit boundary across several mutable objects.
The new [batch API](../../kernel/include/anx/state_object.h) uses their existing staged object representation.

## Implementation

The [stage implementation](../../kernel/core/state/stage.c) accepts writable handles for one through four distinct objects.
Every object must have an open stage with the same non-nil owner.
The implementation copies the object pointers and acquires their locks in object-identifier order.
Interrupts remain disabled until all locks release on the current bootstrap CPU.

Commit validates every target before publication.
The checks cover the active writer, current write ACL, original actor's effect authority, identity, run fence, and branch policy.
Each target must retain its mutable state and staged base version, with room for another version.
Any enrolled evidence review must still approve the exact proposed bytes.
An error preserves all live payloads and all pending stages.

After successful validation, commit replaces each live payload, increments each version once, and recomputes each content hash.
The existing provenance mechanism records each mutation, and each enrolled review resolves as committed.
No model, planner, or external handler runs between validation and publication.
The individual commit API uses the same validation and publication helpers.

Batch abort validates the active writer and shared owner before discarding any stage.
Abort preserves each live payload, version, and content hash.
The existing provenance mechanism records each abort, and enrolled reviews resolve as aborted.
The individual abort API retains its previous behavior.

## Native checks

The [fixture](../../kernel/core/tools/research_day080.c) creates four mutable objects and stages four distinct replacement payloads.
An initial batch abort preserves all original bytes, versions, and hashes and records four aborted stages.
The fixture then retries publication through these rejection cases:

| Condition | Expected result |
| --- | --- |
| Null array, zero count, or count above four | Invalid request; no target changes |
| Read-only handle | Permission failure; all stages remain |
| Repeated object | Duplicate rejection; all stages remain |
| Different staging owners | Permission failure; all stages remain |
| Changed base version | Stale-stage rejection; all stages remain |
| Revoked object write access | Permission failure; all stages remain |
| Revoked side-effect authority | Permission failure; all stages remain |
| Held run fence | Busy result; all stages remain |
| Enrolled review without an approval | Audit failure; all stages remain |
| Foreign active Cell | Commit and abort fail; all stages remain |

Batch abort also resolves the unapproved review without changing any live object.
After fresh staging, the active owner commits all four replacements.
The fixture checks every new payload, changed hash, single version increment, and mutation record.
Repeated commit and abort reject because no pending stages remain.
The supplied handles use reverse creation order; the implementation chooses its own lock order.

## Limits

The transaction covers in-memory payload publication on the current bootstrap CPU.
It does not provide crash recovery, durable transaction logs, nested transactions, process snapshots, or a general multicore reader snapshot.
The batch limit is four objects; payload allocation retains the existing stage allocator's limits.
Provenance retains the existing allocation behavior and is not a durable write-ahead log.

The caller explicitly chooses batch commit or abort.
Existing individual commit calls can still resolve individual stages under their original contracts.
The batch API does not install permanent transaction membership or a shared speculative resource budget.
External calls retain their existing independent admission and journal mechanisms.
Buffering external effects, registering compensations, and admitting irreversible frontiers remain separate work.
No branch-creation, rollback-latency, or memory-amplification improvement is claimed.
