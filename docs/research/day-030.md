# Day 030: Bind routing trials to a declared target and evaluation artifact

The July 25 briefing treats target knowledge and evaluation conditions as explicit, versioned inputs to optimization.
The comparison baseline, `1936ce2`, validates routing actions and policy generations but does not bind those actions to an engine configuration.
A trial can therefore start after the target differs from the environment associated with its proposal.

## Scope

The source is [Day 030 in the daily review](daily-review.md#day-030--2026-07-25).
The source message identifier is `de9ffcd8-6113-4a35-8372-3cba1927e61e`.
This step adds a target contract and sealed artifact to the existing reversible routing trial API.
The artifact binds supplied evidence to a bounded environment description; the artifact does not prove that the evaluation ran.

## Implementation

The [target contract](../../kernel/include/anx/tuning.h) records the compiled kernel profile, selected engine identifier, and a digest of that engine's configuration.
The digest covers engine class, status, capabilities, context limits, network requirements, locality, resource weights, quality, topology affinity, and model descriptor fields.
The encoder hashes each numeric field as eight bytes in little-endian order.
The target also references a sealed knowledge object by identifier, version, payload digest, and sensitivity.

The [artifact constructor](../../kernel/core/route/optimization.c) rechecks the target before storing a routing action and evaluation reference.
Knowledge and evaluation inputs must have nonempty sealed payloads no larger than one MiB each.
The object reader checks current read access and recomputes each payload digest under the object lock.
The resulting structured object uses schema `anx:optimization/route/v1`, version `1`, and provenance parents for both input objects.
The constructor seals the artifact before returning its identifier.

Starting an artifact trial requires the expected object type, schema, version, payload size, and sealed state.
The reader rechecks the evaluation reference before forwarding the action to the tuning gate.
The [tuning gate](../../kernel/core/route/tuning.c) rechecks the target profile, engine digest, and knowledge reference before changing policy weights.
Changed references or engine settings return `ANX_EBUSY`; a missing engine or object returns `ANX_ENOENT`.
An incompatible compiled profile returns `ANX_ENOTSUP`.
Failures preserve the trial output and active policy.

The existing generation check rejects stale policy proposals and overlapping trials.
A matching artifact starts a reversible trial that uses the existing accept or reject operation.
Active cells cannot capture targets, create artifacts, or start policy trials through these APIs.
A completely empty target contract preserves the existing trusted manual control path.
Artifact activation always requires a bound target contract.

The [native regression](../../kernel/core/tools/research_day030.c) rejects a recorded proposal after changing its engine's GPU cost weight.
The fixture also checks a changed model context window, mismatched test mode, changed input labels, and an unsealed artifact.
A matching artifact activates its candidate weights and restores the original policy after rejection.
The test then rejects the stale proposal and a proposal whose engine was removed.

## Limits

The evaluation payload is opaque, and the controller supplies its meaning.
The change adds no correctness grader, benchmark executor, measured speedup threshold, or proof linking an evaluation run to its target.
The VM fixture uses a synthetic evaluation record and measures compatibility enforcement only.

The target covers one engine and the compiled architecture and research mode.
The target does not cover the whole engine registry, driver versions, compiler versions, kernel source hashes, thermal state, or physical accelerator firmware.
The kernel profile and image digest checks from Day 018 remain separate build evidence.

The artifact payload uses the native kernel structure layout and carries no signature or cross-version serialization guarantee.
Target verification and policy activation do not hold a common lock across every mutable registry.
The synchronous fixture does not prove atomicity against concurrent engine removal, object deletion, or configuration changes.
Later target drift does not automatically end an already active trial.
