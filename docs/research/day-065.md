# Day 065: Remove equivalent inference work before scheduling

The August 29 briefing argues that execution structure can dominate later placement or kernel optimization.
It recommends deterministic graph rewrites with explicit authority guards and measurements across the resulting workload.
At comparison baseline `2a46190`, Anunix can prepare verified inference requests but has no compiler that coalesces equivalent requests in a bounded graph.
This step adds literal and reuse plans and compares their completed model work and outputs in the native guest.

## Scope

The source is [Day 065 in the daily review](daily-review.md#day-065--2026-08-29).
The source message identifier is `c4abc0ce-78d5-4add-ac3f-58e82e776015`.
The compiler accepts only existing prepared toy-model requests from Day 064.
It can remove duplicate computation while preserving each logical request's completion record.

The briefing also discusses fusion, pipeline layouts, communication rewrites, and hardware-specific lowering.
This step implements one conservative rewrite and measures it directly.
It does not add a general graph optimizer or change the Resource Twin's placement model.

## Implementation

The [shape compiler](../../kernel/core/workflow/execution_shape.c) supports 16 plans, each containing at most eight inference nodes.
Each node references a distinct prepared model-use record and declares a mask of earlier dependencies.
Only controller code can compile a plan.
Every record must be ready and belong to the specified owner.

The compiler rejects unknown operations, duplicate record identifiers, forward dependencies, cycles, invalid counts, and nonzero unused nodes.
Its private plan copies the specification, captures record epochs, and retains the owner.
Caller edits cannot change the issued graph.

| Plan mode | Physical execution choice |
| --- | --- |
| Literal | Execute every logical request. |
| Reuse | Execute one representative of matching deterministic requests and reuse its result for the others. |

Reuse requires matching owners, signed identity records, source object identities, versions, sizes, sensitivities, source digests, output limits, and request digests.
The dependency masks must also match exactly.
Requests with a nonzero random seed remain separate.
These restrictions exclude authority changes, different source objects, and movement across dependency boundaries.

At execution, the plan checks current owner authority and all prepared record epochs.
Each node then waits for its declared predecessor completions and rechecks its own record.
A physical node uses the Day 064 verified CPU path.
A reused node takes an already completed result through the [private model-use registry](../../kernel/core/anxml/model_use.c).

That reuse operation independently checks both records, current owner authority, source access, source versions, and the cached output digest.
It completes the target record once and records the source record's identifier.
The reused record reports zero newly generated tokens, while retaining the output and consumed-image digests.
A supplied metadata copy cannot authorize reuse.

Plan results include logical operations, planned physical operations, completed computations, reused completions, generated tokens, and a completion mask.
An execution failure stops the plan and prevents logical result reads through the plan API.
Individual model-use receipts remain available to their authorized owner or controller.
Completed-plan reads recheck their source records and current object access.

## Native comparison

The [regression](../../kernel/core/tools/research_day065.c) prepares two sets of the same three requests: `AAAA`, `AAAA`, and `BBBB`.
The third request depends on both earlier logical completions.
The literal plan runs under the controller; the owner executes the reuse plan inside its actual Cell run.
Every corresponding output must match byte for byte.

| Measurement within each three-request plan | Literal | Reuse |
| --- | ---: | ---: |
| Logical completions | 3 | 3 |
| Completed CPU generations | 3 | 2 |
| Reused completions | 0 | 1 |
| Newly generated tokens | 12 | 8 |
| Output sequence | `AAAA`, `AAAA`, `BBBB` | `AAAA`, `AAAA`, `BBBB` |

The guest emits these counts with the output-equivalence result in its serial evidence.
The duplicate's receipt points to its representative and records zero new generation tokens.
The dependency completion mask still contains all three logical nodes.

Other checks reject malformed graphs and foreign-owner requests.
Different dependency masks and matching stochastic seeds each preserve separate physical operations.
Consuming a prepared record outside its compiled plan makes that plan stale before execution.
Revoked prompt access stops a plan without completing any node or exposing a result.

A foreign Cell cannot inspect, execute, or read the owner's plan.
An image-specific result cannot satisfy a request for another image.
Changing the caller's original graph does not alter the issued plan.
Revoking prompt access also prevents later reads of a reused output.

## Limits

This is a bounded inference-plan API, separate from serialized workflow nodes.
Dependencies express completion order; nodes do not dynamically pass generated bytes into another node's prompt.
Execution remains sequential, and equivalence requires exact prepared inputs rather than a claim of semantic similarity.

The comparison counts completed model computations and newly generated tokens inside the two graphs.
It is not an end-to-end latency, energy, throughput, or hardware-launch benchmark.
Failed attempts can perform work before failing; the completed-computation counter does not estimate that wasted work.
Preparation, verification, and the separate negative tests are outside the comparison counts.

Plans and cached results are private and boot-local.
No arbitrary tools, effectful operations, GPU fusion, communication restructuring, or confidential execution backend is added.
The native result does not reproduce the briefing's reported acceleration or establish a general optimizer advantage.
