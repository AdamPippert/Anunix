# Day 007: Invocation accounting

The July 2 briefing identifies a tool invocation as the unit where short resource spikes occur.
Its control loop starts with measurement before scheduler changes.
Anunix already has child slots, engine leases, lifecycle timestamps, and trace events.
The comparison baseline, `2409aff`, has no per-tool byte or timing record and discards the materialized trace identifier.

## Scope

The source is [Day 007 in the daily review](daily-review.md#day-007--2026-07-02).
The source message identifier is `7689695c-608c-474b-b3d2-bc21f885aae4`.
This step measures invocation timing, reported bytes, transport outcome, and child slot ownership.

## Implementation

The cell retains the object identifier returned when its trace is materialized.
The trace records dispatch start and completion times, declared request bytes, handler-reported response bytes, transport result, and application status.
The runtime clears previous response metadata before dispatch.
Failed cells now record their completion timestamp.

The [native regression](../../kernel/core/tools/research_day007.c) creates child tool calls under a parent with one slot.
An admission denial produces no dispatch attempt.
A failing handler and a successful handler each observe the occupied slot and produce separate accounting records.
Destruction returns the slot, and each trace remains readable by object identifier afterward.

## Limits

Elapsed transport time includes handler execution; it is not CPU time.
Byte counts describe the call interface and rely on the trusted handler's reports.
The change does not measure peak memory, CPU utilization, kernel I/O, network packets, or billed cost.
It does not add Linux cgroups or enforce timeouts on a running synchronous handler.
Trace materialization can still fail, leaving a nil object identifier, and the current State Object record is not sealed.
The regression verifies child slot acquisition and release; engine reservation accounting remains the Day 003 check.
