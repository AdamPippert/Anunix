# Day 071: Preserve the logical program while replacing physical plans

The September 4 briefing separates authoritative logical work from provisional physical scheduling decisions.
At comparison baseline `aeea340`, Anunix compiles an execution shape and runs its entire graph through one API call.
This step adds separate logical-graph and physical-plan types.
Each physical plan can commit only the next logical operation.

## Scope

The source is [Day 071 in the daily review](daily-review.md#day-071--2026-09-04).
The source message identifier is `86fbcab7-8cf4-40a0-a928-8253e648b2b8`.
The briefing describes separate logical and physical graphs, short commit prefixes, and revisable scheduling suffixes.
Its research examples include heterogeneous workflow orchestration, Einsummable, and NACRE's separation of resource and state authority.
The native experiment tests preserved semantics across resource-driven replanning.
It does not reproduce those systems' hardware topology, latency, isolation, or throughput results.

## Comparison

Day 065 distinguishes logical operations from physical generation calls and reuses eligible results.
Day 069 separates model readiness from execution readiness across an ordered frontier.
Neither API provides a separately issued physical prefix that can become stale while its logical graph remains valid.

The [new public types](../../kernel/include/anx/physical_plan.h) separate immutable program inputs from issued execution decisions.
The [implementation](../../kernel/core/workflow/execution_shape.c) reuses the existing execution-shape registry and model-use checks.
It reserves the new logical kind for incremental execution.
The older whole-shape run API rejects that kind, so it cannot bypass physical-plan admission.

## Implementation

A logical graph captures up to eight distinct prepared model-use records and their forward dependencies.
The controller creates its specification without choosing a physical mode.
The private record retains the owner, copied nodes, and original source bindings.
A program digest identifies the initial specification and prepared bindings within the current build.
Completed results advance the logical epoch without changing that program digest.

A physical plan captures one logical graph epoch and one current inference-phase epoch.
The compiler selects the next incomplete node whose predecessors have completed.
It permits direct generation or reuse of an eligible completed result.
Reuse requires the same deterministic request, source bindings, owner, identity commitment, and dependency mask.
An incompatible result causes the compiler to select direct generation.

| Boundary | Stable logical state | Provisional physical state |
| --- | --- | --- |
| Program creation | Owner, operations, dependencies, source bindings | No issued plan |
| Physical compilation | Existing program and completed prefix | One selected operation and resource phase |
| Successful prefix commit | New completed result and logical epoch | The issued plan becomes committed |
| Phase resize | Existing program and completed prefix | Earlier phase-bound plans become stale |
| Recompilation | Existing program and completed prefix | A fresh physical decision |

The compiler stores plans in a separate registry of 32 records.
Each plan retains its logical graph until controller cleanup.
Public plan fields are observations; changing a copied node or epoch cannot redirect execution.
The physical plan contains no API for changing the logical owner, dependencies, model sources, or request bytes.

Commit checks both captured epochs before running the selected operation.
The current phase must remain active, and its lease must retain the captured resource dimensions.
Missing, revoked, expired, or changed reservations reject the prefix.
Current owner, scope, identity, scheduler-domain, and model-use checks remain active.
The model-use path verifies sources before returning a result.

Direct prefixes invoke actual verified CPU generation.
Reuse prefixes invoke the existing checked result-reuse path and create a distinct completed model-use receipt.
The logical graph records one completion per accepted prefix.
An older logical epoch cannot commit a competing plan after that completion.
The next operation requires a newly compiled prefix.

Preflight rejection preserves logical progress and caller output.
A started attempt that fails before model-use completion consumes its physical plan but leaves the logical prefix unchanged.
The controller can compile another plan after resolving the failed condition.
A resource change after model-use completion instead marks the logical graph failed to prevent duplicate execution.
The model-use receipt remains inspectable through its existing API.

Only the controller can create graphs, compile plans, and destroy either record type.
The owner or controller can commit an issued prefix and read completed logical results.
Foreign Cells cannot inspect or execute those records.
Issued plans prevent graph destruction, and active execution prevents mutation or cleanup.

## Native checks

The [regression](../../kernel/core/tools/research_day071.c) prepares two equivalent three-node programs.
The reference runs all three operations directly and produces `AAAA`, `AAAA`, and `BBBB`.
The incremental graph begins with two competing plans for its first operation.
Committing one advances the logical epoch, so the other plan fails without changing progress or output.

The fixture compiles a reuse plan for the second operation, then resizes the inference phase.
The stale physical plan fails while the first completed result remains readable.
A fresh plan uses the new phase epoch and reuses the first verified result.
The third operation uses a different model, so its plan requires direct generation.

A revoked prompt read blocks that third plan before model completion.
Restoring access does not revive the consumed physical plan.
A newly compiled plan then completes the graph through the active owner.
The fixture compares all three outputs against the direct reference.

| Fixture result | Direct reference | Replanned prefixes |
| --- | --- | --- |
| Logical completions | 3 | 3 |
| Physical generation calls | 3 | 2 |
| Reused results | 0 | 1 |
| Generated outputs | `AAAA`, `AAAA`, `BBBB` | `AAAA`, `AAAA`, `BBBB` |
| Program digest after physical changes | Not measured by the legacy API | Unchanged |

The fixture also rejects foreign model-use bindings, malformed dependencies, and a legacy shape presented as a logical graph.
Mutating the original logical specification and copied physical plan cannot change the private program.
A foreign active Cell cannot read or commit the final prefix.
The active owner completes the final operation and reads every committed result.

## Limits

The physical choices are direct toy-model generation and compatible result reuse on the existing CPU path.
The phase epoch represents the modeled resource configuration; it is not a complete hardware-topology snapshot.
This step adds no GPU placement, network execution, model residency fusion, or automatic telemetry-driven replanning.
The controller explicitly recompiles each next prefix.

The graph and plan types are private runtime records with distinct API schemas.
They are not serialized, sealed State Objects or portable execution formats.
The program digest uses the current build's prepared-record representation and does not provide cross-build attestation.
Source and authority checks enforce execution; the digest alone grants no permission.

The experiment demonstrates output equivalence and preserved logical progress across physical-plan invalidation.
It does not establish tail-latency improvements, planner overhead, or the briefing's proposed performance thresholds.
Existing model-use records retain their own lifetimes and require separate controller cleanup.
All graph and plan state remains within the current boot.
