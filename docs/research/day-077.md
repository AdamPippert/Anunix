# Day 077: Reduce generation work within a fixed quality contract

The September 10 briefing treats the amount of computation as a scheduling variable.
At comparison baseline `eeb5047`, Anunix checks token ceilings and physical plans without a separate catalog of quality-admitted workload choices.
This step admits deterministic candidates against a frozen output check before selecting a generation budget.
A smaller admitted candidate can reduce generation work while retaining the declared output requirement.

## Scope

The source is [Day 077 in the daily review](daily-review.md#day-077--2026-09-10).

The briefing discusses PELM's computation controls, Avatar's control timescales, proxy execution, frozen optimization tests, and deterministic proposal management.
The native experiment tests workload selection within fixed quality and token bounds.
It adds no frequency governor, thermal controller, learned policy, or control-loop latency contract.

## Comparison

The cognitive envelope limits each generation request.
Model-use records bind exact source objects, request bytes, owner identity, and verified CPU results.
Physical plans choose when and where an operation consumes its sources.
These checks do not identify which cheaper generation configurations preserve a caller's declared output requirement.

The [workload API](../../kernel/include/anx/workload.h) adds a controller-owned candidate catalog and current selection.
The [implementation](../../kernel/core/route/workload.c) uses completed model-use receipts as admission evidence.
It keeps the quality contract separate from the mutable choice of candidate and token ceiling.

## Implementation

The controller creates an immutable contract containing an expected output prefix, output-length bounds, and a maximum token allowance.
Prefix and output lengths use bytes; the token allowance uses generated tokens.
The implementation supports output and token bounds up to 128.
It retains the owner, owner ancestry, and identity record.
The registry holds at most 16 workloads with eight candidates each.

Candidate admission needs a completed model-use receipt from the same owner and identity.
The receipt must represent actual generation with deterministic sampling, rather than reused output.
The candidate's token allowance must fit the contract.
The runtime reads the checked result and tests its prefix, output length, and generated token count.
Failed admission preserves the catalog and current selection.

The controller selects an admitted candidate against the current workload epoch.
The requested token limit must cover that candidate and remain within the frozen contract.
Selection rechecks the candidate receipt and its current source objects.
Success advances the epoch and records the selected candidate and limit.
Failure leaves the existing selection unchanged.

Execution needs a fresh prepared model-use record matching the selected candidate's owner, identity, sources, request, and token allowance.
The runtime rechecks the sample before dispatch and invokes actual verified CPU generation.
It checks the resulting bytes against the frozen quality contract before returning output.
An execution in progress blocks catalog changes, selection, and destruction.

Each started attempt advances the workload epoch and records its result.
Completed model-use generation increments the execution and token counters, including a later rejected output.
Preflight rejection leaves counters and caller output unchanged.
Failed attempts preserve caller output; the workload record exposes the latest result through inspection.

Only the controller can create workloads, admit candidates, select a configuration, and remove records.
The owner or controller can execute the selected configuration and inspect its record.
Foreign Cells cannot inspect or execute the workload.
Copied contract and view fields cannot change the private admission requirements.

## Native checks

The [regression](../../kernel/core/tools/research_day077.c) fixes the required prefix to `AAAA` and accepts output lengths from four through eight bytes.
Its frozen maximum allowance is eight tokens.
The fixture generates calibration results before offering five candidates to the workload controller.

| Candidate | Generated output | Admission |
| --- | --- | --- |
| Eight-token configuration | `AAAAAAAA` | Accepted |
| Four-token configuration | `AAAA` | Accepted |
| Two-token configuration | `AA` | Rejected: output too short |
| Different model with four tokens | `BBBB` | Rejected: wrong prefix |
| Sixteen-token configuration | Sixteen `A` bytes | Rejected: token allowance exceeds contract |

Changing the original contract copy cannot admit the rejected candidates.
Duplicate admission also fails without changing the workload.
Selecting the eight-token candidate under a four-token limit preserves the prior selection.
An excessive limit, unknown candidate, stale execution epoch, and mismatched prepared request also fail.

The accepted eight-token configuration executes and produces `AAAAAAAA`.
Corrupting its shared prompt blocks a later selection without changing the active plan.
After restoring the prompt, the controller selects the four-token candidate under a four-token limit.
The active owner executes that selection and produces `AAAA`.
Both results satisfy the same frozen prefix check.

The workload records two runtime executions and 12 generated tokens.
The second execution uses four tokens instead of eight.
The fixture also rejects foreign execution and active-Cell attempts to change the controller's contract or selection.

## Limits

Quality means the declared byte prefix and output-length bounds in this experiment.
It does not measure semantic correctness, model reasoning quality, downstream task success, or statistical accuracy.
The deterministic model and exact request bindings make the calibration check reproducible within this fixture.
They do not establish generalization to new prompts or models.

Calibration runs occur outside the workload's runtime counters.
The fixture executes five calibration samples before the two selected runtime executions.
The token reduction describes the selected runtime configuration, not an end-to-end cost reduction including calibration.
No latency, resource-time, energy, thermal, or frequency improvement is claimed.

The controller supplies each selection; the implementation adds no optimizer or telemetry policy.
Each execution still has its own model-use receipt and existing cognitive limits.
Sample receipts must remain available for future admission checks; removing a sample blocks later use of that candidate.
The API is explicit and does not change unrelated generation paths.
All workload state remains within the current boot.
