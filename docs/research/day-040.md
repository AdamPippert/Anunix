# Day 040: Validate typed policy intent before evaluation and activation

The August 4 briefing proposes compiling optimization intent into typed variables, measurable constraints, and a bounded evaluation problem.
The comparison baseline, `ff29ee6`, validates routing weights and binds target profiles to issued harness receipts.
The baseline has no typed task that carries variable domains, units, source labels, and hard constraints through evaluation.

## Scope

The source is [Day 040 in the daily review](daily-review.md#day-040--2026-08-04).
The source message identifier is `e7cc63e2-9a8d-424f-9050-637fa34a1080`.
The briefing assigns policy discovery to an offline process and deterministic enforcement to the runtime.
This step adds a finite task representation for the existing routing policy and harness.
The baseline adapter copies the declarations without validating their feasibility.

## Implementation

The [task compiler](../../kernel/core/route/policy_task.c) accepts eight ordered routing variables and one through four distinct constraints.
Each range declares a unit and an operator or default source label.
The variable order matches the existing routing weight structure.
Bounds must remain within the kernel's supported domains and contain the proposed value.

| Declaration | Unit | Supported domain |
| --- | --- | --- |
| Locality, local-first, private-data, and topology-overlap bonuses | Score points | 0 through 1000 |
| Degraded and topology-mismatch penalties | Score points | -1000 through 0 |
| GPU and CPU divisors | Divisor | 1 through 1000 |
| Feasible engine count | Engines | 0 through 32 |
| Winner margin | Score points | 0 through 6300 |
| Winner CPU or GPU cost | Relative cost weight | 0 through 100 |

Defaults use the full variable domains and require at least one feasible engine.
Callers can narrow those ranges and supply constraints before compilation.
Compilation rejects contradictory ranges, unsupported metrics, incorrect units, missing source labels, duplicate constraints, and out-of-domain candidates.
A failed compilation leaves its output unchanged.

Evaluation, artifact creation, and trial admission repeat task validation rather than trusting the compiler call.
The [fixed harness](../../kernel/core/route/optimization_harness.c) applies each declared constraint to every simulated case.
A missing winner or unavailable margin fails a constraint that requires that observation.
The harness retains its existing local-winner requirements.

The receipt digest now includes every task field as well as the existing action and target data.
A compiled task requires a current, privately issued passing receipt before trial admission, including through the direct admission API.
The gate checks the receipt object's sealed state and payload digest before accepting its issuance record.
Changing a task after evaluation invalidates that evidence binding.

An all-zero task retains the existing manual control path and revision-authority checks.
Native routing artifacts now use `anx:optimization/route/v2` and schema version `2` because the payload includes the task.
The artifact reader rejects the earlier layout; callers must create a new artifact under the current build.

The [native regression](../../kernel/core/tools/research_day040.c) rejects an impossible count range before compilation, evaluation, or trial admission changes any output.
It checks incorrect units, unsupported metrics, omitted source labels, and a candidate outside its declared range.
The two-engine requirement fails three fixed cases and cannot authorize activation.
The valid task passes evaluation, enters a trial, and restores the original weights on rejection.
The fixture also rejects a changed task attached to an earlier passing receipt.

## Limits

The compiler accepts an explicit native structure; it does not parse natural language, infer operator facts, or invent numerical defaults.
Source labels declare provenance but do not authenticate who supplied a value.
The finite domains establish structural feasibility; harness execution checks the declared constraints against four fixed cases.

CPU and GPU cost weights are relative routing metadata, not measured hardware utilization.
Winner margins are deterministic score differences, not probability or task-quality estimates.
The change adds no latency, energy, starvation, or external-effect metric without a corresponding observer.

The task representation does not search for weights, rank competing objectives, generate executable code, or establish a production performance optimum.
The checks bound the existing simulation and promotion path without a workload-wide safety proof.
Receipt validation and trial activation retain their separate locks and existing concurrency limits.
