# Day 033: Enforce revision authority at typed operations

The July 28 briefing distinguishes parameter tuning, implementation replacement, and changes to system authority.
The comparison baseline, `e534009`, blocks active cells from routing trials but permits capability installation through existing execution permissions.
Those permissions cannot express a grant for parameter tuning without implementation replacement.

## Scope

The source is [Day 033 in the daily review](daily-review.md#day-033--2026-07-28).
The source message identifier is `9497f51e-3371-473c-a157-70c6a0b61e6e`.
This step adds revision leases with two ordered classes: parameters and implementation.
Existing C APIs define the operation types; callers cannot label an implementation change as a parameter change.

## Implementation

The [lease registry](../../kernel/core/cap/revision.c) stores an immutable authority ceiling and a revocation flag behind each identifier.
The registry supports 256 leases and returns value copies for inspection.
Trusted control code issues, binds, and revokes leases outside active execution.
The binding API accepts only a fresh root with no previous lease.
Child derivation inherits the binding, and runtime ancestry checks reject a different child binding.

| Operation | Required class | Enforcement |
| --- | --- | --- |
| Begin a routing trial | Parameters | Bounded typed weights, current generation, and existing target checks |
| Finish a routing trial | Parameters | Active caller owns the trial, or trusted control performs recovery |
| Install a capability | Implementation | Revision ceiling plus existing authority, dependency, lifecycle, and promotion checks |
| Remove an installed capability | Implementation | Revision ceiling before engine removal |
| Change an installed capability lifecycle | Implementation | Revision ceiling before the status change |
| Issue or widen authority | Trusted control | Active cells cannot issue leases or change a capability authority ceiling |

The [routing trial path](../../kernel/core/route/tuning.c) admits an active cell only with an explicit parameter grant.
Both grant classes permit parameter changes, within the existing numeric bounds.
A bound operation rechecks revocation, side-effect permission, terminal state, identity, and the run fence.
An unbound active caller remains unable to tune routing.
Unbound capability operations retain their existing authorization behavior.

The [capability path](../../kernel/core/cap/capability.c) classifies installation, removal, and installed lifecycle changes as implementation revisions.
A parameter grant returns `ANX_EPERM` before those changes.
An implementation grant permits them only after the existing checks pass.
An implementation grant does not permit changes to its own ceiling or to capability authority.

The [native regression](../../kernel/core/tools/research_day033.c) exercises a child with an inherited parameter grant.
The fixture rejects installation, removal, suspension, authority expansion, lease issuance, rebinding, and revocation from that child.
The fixture rejects an invalid routing divisor, permits a bounded trial and rollback, and rejects acceptance from a different cell.
An implementation grant permits installation; revocation then blocks removal and parameter tuning.

## Limits

The implementation defines two revision classes; it provides no architecture-rewrite interface or operator signature protocol.
The change adds no general policy language, eBPF backend, cross-boundary compiler, or performance benchmark.
Existing artifact activation still requires trusted control and harness evidence.
The granted parameter path uses the existing manual trial API and its numeric checks.

The registry remains volatile and does not recycle identifiers.
Revocation and mutation do not share one transaction across all subsystem locks.
The synchronous VM tests do not establish atomic revocation during concurrent mutation.
Trusted kernel code can still mutate native structures directly; these gates do not isolate arbitrary kernel code.
