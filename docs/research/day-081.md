# Day 081: Select a policy from an issued catalog

The September 14 briefing separates policy construction from runtime selection.
The source message is `2b0646b7-8ce0-4118-a447-80e8979d269b` in the [research conversation](https://chatgpt.com/c/6a3eabf4-cb88-83ea-942e-a601dd12b392).
Its central lesson gives the runtime controller a categorical choice among previously validated behaviors.
The briefing also distinguishes a safe actuator from evidence that an LLM makes better decisions than simpler controllers.
The Anunix experiment applies that boundary to its existing finite routing profiles.

## Comparison

| Area | Existing Anunix | Day 081 change |
| --- | --- | --- |
| Policy construction | The controller compiles and issues a profile for finite routing cases | Catalog creation accepts only profiles that pass current validation |
| Runtime input | A Cell names a profile object | A Cell supplies a catalog identifier, epoch, and bounded integer index |
| Catalog authority | No common owner or version exists across a profile set | One private catalog binds its entries to an owner and epoch |
| Failure | A rejected individual profile retains incumbent weights | Invalid, stale, revoked, or foreign catalog selections retain those weights |

The [Day 044 profile compiler](day-044.md) records the build, incumbent policy, finite cases, and resource environment.
The [Day 047 compiler budget](day-047.md) bounds its representations and simulation calls.
The new [catalog API](../../kernel/include/anx/route_catalog.h) groups those issued artifacts without accepting runtime code or weight parameters.

## Implementation

The [catalog registry](../../kernel/core/route/catalog.c) holds at most 16 catalogs, with one catalog per owner.
Each catalog contains one through four distinct profile identifiers.
Only the controller can create, replace, or destroy a catalog.
Creation retains the owner and captures its parent and admitted identity record.
The catalog starts at epoch one.

Creation and replacement validate every profile against the owner's current routing case, build, incumbent policy, and environment.
An invalid member rejects the complete set.
Successful replacement increments the epoch once and publishes the new private entry array.
A stale replacement request leaves the existing catalog and caller output unchanged.
The owner can inspect a copy; changing that copy cannot change catalog membership.

The [route planner](../../kernel/core/route/planner.c) reads the Cell's catalog identifier, epoch, and index as untrusted inputs.
The catalog checks the exact owner, active caller, current scope, contract, scheduler domain, identity, ancestry, and run fence.
It then checks the selected profile's current issuance, content, access, build, finite case, incumbent generation, and resource environment.
Only successful selection replaces the weights for that routing calculation.
The global policy remains unchanged.

A catalog error records its status and retains the current incumbent weights.
An explicit catalog selector takes precedence over the older individual profile field.
Rejection cannot fall through to a different profile named in that older field.
The planner still performs its normal feasibility checks before choosing an engine.
Catalog failure permits default routing; it does not grant permission to dispatch a held or unauthorized operation.

## Native checks

The [fixture](../../kernel/core/tools/research_day081.c) compiles three profiles with different locality bonuses for one finite routing case.
The planner selects every index and produces the expected scores for a registered engine.
A copied catalog with altered entries does not change those results.

The fixture verifies default-policy routing for these rejected selections:

- An index equal to the entry count or the largest unsigned integer.
- An unknown catalog or stale catalog epoch.
- A corrupted profile payload or revoked read access.
- A changed engine environment or held run fence.
- A released profile, including a catalog that still names its former identifier.
- A foreign owner, foreign active caller, terminal owner, or destroyed catalog.

A forged sealed profile cannot enter the catalog, and its failed replacement preserves the old selection.
Repeated entries and counts outside one through four reject.
A valid replacement reverses the three entries and advances the epoch to two.
The old selector becomes stale; an updated selector uses the new entry order.
The active owner selects all three policies but cannot create, replace, or destroy a catalog.
The fixture compares the global tuning state before and after the sequence and finds no change.

## Limits

The catalog is an optional routing interface, not a Linux `sched_ext` scheduler or eBPF program array.
Profiles certify winner preservation for recorded cases and an exact environment; they do not prove correctness for every workload.
Runtime selection still performs profile validation and allocations.
No nanosecond switching cost, latency improvement, throughput gain, energy saving, or LLM advantage is claimed.

The controller chooses catalog membership; the experiment does not supply an autonomous selector or train a routing model.
The fixture varies routing weights while preserving the finite case's winner.
It does not demonstrate distinct CPU preemption algorithms or a production scheduling policy comparison.
Existing callers with all catalog fields zero retain the individual-profile path.
Clearing those optional fields does not install a mandatory catalog policy on the Cell.
Catalogs and their epochs are in-memory state and do not survive a reboot.
