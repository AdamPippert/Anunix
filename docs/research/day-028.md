# Day 028: Carry read sensitivity across a run's later effects

The July 23 briefing argues that authorization must consider prior actions and data lineage across a trajectory.
The comparison baseline, `ca41ae4`, checks an effect's declared object label and maintains a shared run fence.
A branch can read confidential data without constraining a sibling's later effect that names a public object.

## Scope

The source is [Day 028 in the daily review](daily-review.md#day-028--2026-07-23).
The source message identifier is `42b27027-d6d6-4591-9e36-ad4a065f6657`.
This step adds a deterministic rule to the existing run fence: sensitive reads constrain later protected effects across that run.
The briefing describes ChainWatch as a design specification, without validated detection rates or production overhead.

## Implementation

The [run fence](../../kernel/include/anx/effect_fence.h) starts with public sensitivity, a nil source identifier, and zero reads.
The fence retains the highest sensitivity observed through successful nonempty payload reads by its bound cells.
The first object that raises that level becomes the recorded source at that level.
The read count saturates at the maximum unsigned 64-bit value.
Read observations do not change the control generation or run epoch.

The [payload reader](../../kernel/core/state/objstore.c) records the observation before copying bytes to the caller.
The object lock covers the label observation and payload copy.
Zero-length reads and reads beyond the payload do not change the trajectory.
A failed open never reaches the observation hook.
An invalid label or missing bound fence blocks the read without copying bytes.

The [effect checks](../../kernel/core/cap/effect.c) require a destination ceiling that covers the accumulated sensitivity.
A missing destination cannot accept effects after a nonpublic read.
The final dispatch gate repeats this check while holding the same lock that records read observations.
An effect prepared before a sensitive read can therefore fail at dispatch, retaining its `PREPARED` state.
An effect already in dispatch can still settle.

The accumulated sensitivity persists across sibling creation, object relabeling, object deletion, and a hold followed by release.
The run has no operation to lower its recorded sensitivity.
Active cells cannot register destination grants or reset the destination registry.
Trusted control code can still register a destination whose ceiling covers the accumulated sensitivity.

The [native regression](../../kernel/core/tools/research_day028.c) allows the confidential read and rejects the sibling's prepared public transmission.
The fixture also rejects a new public transmission and a destinationless effect after that read.
Denied reads leave the history unchanged, while an approved destination and an unrelated run retain permission.
The test checks failed attempts to widen or reset destination grants from the reader's active cell.

## Limits

The rule applies to bound run fences and effects that use the protected-effect API.
Unbound cells retain the previous behavior.
Direct payload pointers, raw kernel transports, and external handlers outside this protocol remain trusted paths.
This step does not provide process isolation or prevent arbitrary kernel code from bypassing mediation.

The rule conservatively constrains every later effect, even without evidence that the effect actually carries the sensitive bytes.
The recorded source identifies the first read at the highest level; the source does not represent a complete causal graph.
The change adds no injection classifier, cross-server analysis, declassification protocol, or false-positive measurement.

The history uses the existing volatile registry, limited to 256 run fences per boot.
The change adds no restart recovery, persistent trajectory log, or identity-bound protection against creating a new run.
The synchronous fixture does not establish safety under arbitrary concurrent cell, object, or destination mutation.
