# Day 019: Keep capability authority under independent control

The July 14 briefing separates mutable capability assets from the authority that permits their installation and execution.
The comparison baseline, `074b3ec`, checks capability lifecycle and promotion scores but has no independent authority ceiling.
Anunix's credential store holds secrets; the credential store does not supply a capability grant mechanism.

## Scope

The source is [Day 019 in the daily review](daily-review.md#day-019--2026-07-14).
The source message identifier is `c20ed7d5-7da3-4ba6-ba26-549efe59e0c5`.
This step governs declared execution requirements during capability installation and replacement promotion.
Computational input and output capability masks remain separate from execution authority.

## Implementation

Capabilities now declare requirements for network access, remote models, child derivation, and side effects.
The new `required_authority` mask defaults to zero.
Unknown bits return `ANX_EINVAL` during validation or installation.

The capability store keeps grants and installed authority outside the mutable capability declaration.
A fresh capability's authority ceiling defaults to zero.
Trusted kernel control code can set that ceiling only for a fresh draft outside an active cell execution.
The setter rejects active cells, validated capabilities, and candidates that declare an incumbent with `ANX_EPERM`.

Fresh installation requires the declaration to fit the independent ceiling.
Replacement installation requires the declaration to fit the incumbent's recorded installed authority and pass the existing performance gate.
Unused permissions in the incumbent's original ceiling do not transfer to its replacement.
Changing the incumbent's public declaration cannot enlarge the recorded installed authority.

An active promoting cell also needs permission for side effects and every declared execution requirement.
The installer rejects a terminal caller or a missing caller identity.
All authority checks precede engine registration.
Rejected candidates retain their validated state, and the incumbent retains its engine.

The [native regression](../../kernel/core/tools/research_day019.c) checks ungranted installation, declaration tampering, unused grants, and a second replacement generation.
The regression accepts a replacement within scope only after the performance gate passes.
Active caller checks cover missing network, remote-model, and child-derivation permissions, followed by an authorized installation.
The same callers cannot grant their own draft a broader ceiling.
The implementation is [capability.c](../../kernel/core/cap/capability.c), with declarations in [capability.h](../../kernel/include/anx/capability.h).

## Limits

The authority ceiling governs installation of a declared contract; Anunix still lacks a capability procedure interpreter.
The change does not sandbox arbitrary capability code or prove that a declaration describes every effect of future execution.
Cell execution policies remain the runtime enforcement mechanism for implemented operations.

Trusted kernel code can still access raw memory and change lifecycle fields.
The private record is a software boundary within the current synchronous kernel, without hardware isolation or concurrent promotion transactions.
Promotion retains the incumbent and adds a candidate engine; promotion does not switch an active-version pointer atomically.
This step adds no signed artifact registry, automatic synthesis, credential binding, or benchmark authenticity proof.
