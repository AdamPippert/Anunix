# Day 027: Require capability dependencies before installation

The July 22 briefing treats persistent skills as versioned packages with dependencies, permissions, evaluation contracts, and deployment controls.
The comparison baseline, `3c650e5`, already has capability identities, lifecycle states, authority ceilings, and a measured promotion gate.
One missing required engine only lowers the validation score to 75, so that package can still validate and install.

## Scope

The source is [Day 027 in the daily review](daily-review.md#day-027--2026-07-22).
The source message identifier is `f78a94e9-de8d-40bb-ab51-35b163f06800`.
This step strengthens dependency readiness in the existing capability package lifecycle.
The existing permission ceiling remains a separate installation requirement.

## Implementation

The [capability validator](../../kernel/core/cap/capability.c) requires nonempty, terminated names and versions.
The declaration accepts at most eight required engine identifiers, with no nil identifiers or duplicates.
Malformed declarations return `ANX_EINVAL` without changing the lifecycle state or validation score.

Every required engine must exist and have status `AVAILABLE` or `DEGRADED`.
A missing engine returns `ANX_ENOENT`; an unavailable engine returns `ANX_EPERM`.
Both failures leave the capability in `DRAFT` with score zero.
A complete declaration with ready dependencies receives structural score 100 and transitions to `VALIDATED`.

Installation repeats declaration, authority, and dependency checks before registering the capability engine.
These checks also apply to the existing gated installation path.
Removing or draining a dependency after validation therefore blocks installation.
A failed installation preserves the validated state and does not register an engine.

The [native regression](../../kernel/core/tools/research_day027.c) reproduces the missing dependency failure and checks malformed dependency lists.
The fixture also checks invalid names, an unterminated version, and an offline dependency during validation.
Installation rejects a removed dependency, a draining dependency, and an oversized list introduced after validation.
An overprivileged package remains blocked despite ready dependencies.
An authorized package with a degraded dependency installs successfully.

## Limits

Structural score 100 does not measure behavioral competence or task success.
The change adds no procedure interpreter, isolated evaluator, skill retriever, or package rollout controller.
The briefing's reported retrieval and debugging results were not reproduced in this VM.

Dependencies reference engine identifiers without semantic version constraints or recursive dependency graphs.
Capability declarations remain mutable; installation checks the current declaration rather than an immutable evaluated package digest.
The change does not enforce first-attempt grading or preserve an evaluation environment.

Dependency checks cover validation and installation, not automatic suspension after a later dependency failure.
The existing engine registry returns raw pointers without a lifetime reservation.
The synchronous fixture does not establish atomicity against concurrent engine removal or declaration mutation.
