# Day 031: Require a harness-issued receipt for optimization artifacts

The July 26 briefing assigns correctness checks, reference outputs, measurement rules, and promotion evidence to an authoritative harness.
The comparison baseline, `7af3018`, checks target compatibility but treats the evaluation payload as opaque.
A caller can seal its own pass claim and use that object to start an artifact trial.

## Scope

The source is [Day 031 in the daily review](daily-review.md#day-031--2026-07-26).
The source message identifier is `2b5bed64-2acb-4d7b-a1a7-0ef932383afd`.
This step adds a compiled routing harness and requires its receipt at artifact activation.
The harness establishes four routing outcomes; the harness does not measure GPU performance or general candidate correctness.

## Implementation

The [harness](../../kernel/core/route/optimization_harness.c) owns two fixed engine snapshots and four routing scenarios.
The local engine has quality score 50, and the remote engine has quality score 60.
Each case requires the local engine as its reference winner.
The candidate supplies routing weights and target bindings, with no interface to change the cases or expected winners.

| Case | Fixed condition | Required outcome |
| --- | --- | --- |
| Local preference | Both engines available under local-first routing | Select the local engine |
| Local-only constraint | Remote placement prohibited | Select the local engine |
| Network denial | Remote engine requires network access | Select the local engine |
| Remote-model denial | Remote model permission disabled | Select the local engine |

The harness runs the existing Resource Twin simulation against every case.
Every completed evaluation produces a sealed receipt containing the observed winners and failure count.
The receipt uses schema `anx:evaluation/route-harness/v1`, version `1`.
A digest binds the complete action, including weights, policy generation, target profile, engine fingerprint, and knowledge reference.
The encoder uses fixed-order numeric fields and both input digests, without hashing structure padding.

A private registry records the issued receipt identifier, action digest, payload digest, and harness result.
The registry reserves a slot before evaluation and releases that reservation after an error.
The registry supports 32 outstanding receipts, including receipts for failed evaluations.
Trusted control can revoke a receipt while retaining its sealed object for audit.

The [artifact activation path](../../kernel/core/route/optimization.c) now checks private issuance after reading and validating the evaluation object.
An unissued, mismatched, failed, or revoked receipt returns `ANX_EPERM` before policy activation.
A missing evaluation object returns `ANX_ENOENT`.
An exact payload copy with a new object identifier does not inherit issuance.
The existing target and policy-generation checks still apply after the receipt check.

The [native regression](../../kernel/core/tools/research_day031.c) rejects a caller-authored pass claim and a copied harness receipt.
The fixture also rejects a changed candidate, a failed evaluation, a revoked receipt, and a missing evaluation object.
A passing receipt starts a reversible trial, which the fixture rejects to restore the original weights.
An active cell cannot issue or revoke receipts.
The Day 030 fixture now obtains a harness receipt before testing its original target-compatibility checks.

## Limits

The four scenarios define a narrow local-routing contract, not a universal policy objective.
The harness does not test throughput, latency, energy, numerical GPU correctness, cold starts, or workload-specific quality.
The VM fixture establishes enforcement and reference outcomes without reproducing the briefing's reported speedups.

Receipts attest to execution of these compiled cases within the current kernel instance.
The registry is volatile, and receipt payloads carry no signature or cross-host attestation.
The implementation adds no durable issuance recovery, automatic receipt expiry, or general harness-plugin registry.

Trusted manual tuning remains available outside active cells through the existing API.
The change does not isolate arbitrary kernel code or prevent direct mutation of kernel memory.
Receipt checking and trial activation do not share one lock across revocation and every mutable target object.
The synchronous fixture does not establish atomicity under concurrent controller changes.
