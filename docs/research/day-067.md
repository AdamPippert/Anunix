# Day 067: Preserve a continuation across worker replacement

The August 31 briefing separates a long-lived continuation from its replaceable capability processes.
It proposes independent state records, small capability boundaries, and recorded completion before notification.
At comparison baseline `efe64c7`, Anunix has workflow checkpoints, derived Cells, and protected external operations.
This step preserves a logical owner, capability bindings, and completed results when native workers are replaced.

## Scope

The source is [Day 067 in the daily review](daily-review.md#day-067--2026-08-31).
The source message identifier is `26a8ff69-2235-4a97-9c44-c1ba8d2f559f`.
The briefing describes Logos and Cordis and discusses a broader architecture for durable continuations and capability processes.
The native experiment uses Anunix Cells and existing provider callbacks.
It does not reproduce those systems' process isolation, restart experiments, or performance measurements.

## Implementation

The [continuation registry](../../kernel/core/workflow/continuation.c) supports 16 logical records, each with four capability slots and eight operation keys.
Each record retains one owner and captures its execution permissions, constraints, cognitive envelope, contract, and authority bindings.
Current identity, scheduler-domain, scope, and effect-fence checks remain necessary.
Changing the owner's captured policy invalidates further use of the record.

A capability slot names a direct child Cell and a binding generation.
The child must be an unused external-call Cell with a valid inherited scope.
A worker cannot occupy two registry slots, including slots in another continuation.
Replacement requires the previous worker to reach a terminal state.
The registry releases the old worker reference after it records the new binding.

Each operation key identifies one submitted call within its continuation.
A repeated key fails before dispatch, including after worker replacement.
A separate read returns an already recorded result.
Replacement never transfers ownership of the continuation to its new worker.

The controller supplies a registered provider, named Sink, and sealed source object.
The request contains 1–4096 bytes and must match the source payload exactly.
The existing protected-operation API copies the descriptor and binds the provider generation, worker, Sink, and source version.
The registry records a sealed intent before entering the worker.

A private bridge admits only the worker selected by the registry's current operation.
That bridge calls the existing protected dispatcher inside the worker's actual runtime context.
The dispatcher checks the worker's authority and invokes the registered provider once.
Provider re-entry encounters the existing dispatch fence.

| Stage | Preserved state | Visible behavior |
| --- | --- | --- |
| Bind | Worker identifier, slot, and new generation | The slot resolves to the replacement worker. |
| Intent | Operation key, source identifier, and request digest | The key becomes unavailable for another submission. |
| Commit | Sealed response and completion event | The owner can read the recorded response. |
| Uncertain result | Retained key and uncertain state | Automatic retry and registry destruction are blocked. |
| Rejected attempt | Recorded failure before provider dispatch | The same key remains unavailable. |

The registry seals the response and completion event before it exposes completion to the caller.
Each event includes the previous event's identifier and digest.
The bounded transcript contains at most 32 events and preserves their order.
Internal reads check actual payload digests, versions, schemas, sealing, sensitivity, and the logical owner's current access.
The registry checks the transcript before binding, dispatch, projection, or result reads.

Result reads also recheck the original source and sealed response.
The event and response objects use a restricted sensitivity label and an owner-only access policy.
Internal controller reads apply the owner's policy explicitly.
Active reads retain the existing effect-fence observation of object sensitivity.

An uncertain outcome keeps its key and owner references during the current boot.
A later worker can serve a different key, but it cannot repeat the uncertain operation.
The registry has no reconciliation operation that converts uncertainty into permission to retry.
Capacity exhaustion rejects further submissions.

## Native checks

The [regression](../../kernel/core/tools/research_day067.c) binds two workers to one logical owner.
It checks stale epochs, foreign workers, duplicate bindings, premature replacement, and widened child permissions.
A changed owner policy and a request that differs from its sealed source fail before provider invocation.

A test-only fault drops the first completion reply after the result is sealed.
The caller receives a timeout with unchanged output.
A subsequent projection reports one recorded completion.
The fixture replaces and destroys that worker, then reads the original response without another provider invocation.

A failed idle peer also permits replacement.
The two surviving slots execute distinct operation keys and produce three recorded completions.
The logical owner and its network permissions remain unchanged.
Provider re-entry fails before another protected dispatch.

The fixture changes transcript versions, bytes, and access rules.
Those changes block projection without modifying the caller's output.
Source version changes, byte changes, and revoked access likewise block recorded-result reads.
A foreign active Cell cannot read the registry or open its sealed transcript through the object API.

A separate continuation receives a provider timeout and retains an uncertain key.
Replacing its failed worker does not permit a second submission with that key.
The healthy continuation retains its three completions and readable response.
The uncertain record remains allocated for inspection, as required by its retry restriction.

## Limits

This prototype preserves logical state across native worker replacement during one boot.
Its sealed objects use the current in-memory object store and native structure representation.
It does not recover a registry from disk, survive power loss, or provide distributed consensus.
The earlier workflow checkpoint API remains a separate mechanism.

Workers use cooperative Cells and synchronous provider callbacks in the same kernel.
An explicit failed state and a lost completion reply test lifecycle behavior; they do not establish address-space fault containment.
The prototype does not create POSIX processes, an IPC bus, or a general plugin graph.
It makes no latency, isolation-cost, or scheduling-efficiency claim.

A bound tool namespace currently returns `ANX_ENOTSUP` when creating the continuation.
The private bridge has no catalog entry that could satisfy such a namespace.
The implementation does not weaken namespace checks to admit it.

A provider success followed by failed evidence publication leaves the operation uncertain and hides its output.
The implementation cannot roll back an external effect or determine whether an unresponsive provider performed it.
It prevents duplicate submission for retained keys; it does not promise exactly-once effects across a restart.
Removing a completed registry preserves its sealed objects until explicit object cleanup.
