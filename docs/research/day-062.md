# Day 062: Give required branches and trials different completion rules

The August 26 briefing distinguishes required subtasks from competing reasoning trials.
Required groups need every result, while trial groups can stop after accepting a useful alternative.
At comparison baseline `7c3a1f5`, Anunix workflows have fan-out and barrier nodes, but no explicit trial winner or loser-cancellation rule.
This step adds bounded native model-branch groups with different completion semantics and a shared token budget.

The source is [Day 062 in the daily review](daily-review.md#day-062--2026-08-26).

The implementation executes the existing toy CPU model through real child Cells.

Anunix retains its existing workflow representation and backend selection for those concerns.
This step adds branch semantics through a separate native group API; it does not change serialized workflow nodes.

## Implementation

The [group registry](../../kernel/core/workflow/branch_group.c) holds up to 16 groups with at most eight branches each.
A controller supplies one sealed byte-data prompt, required or trial semantics, candidate adapter images, expected outputs, and a token budget.
The prompt must contain 1–1024 bytes.
Each candidate permits 1–128 output tokens, and a group permits at most 1024 charged tokens.

The group copies its specification and derives pure child Cells from its owner.
Every child references the same prompt object and receives its candidate's token ceiling.
Private registry references prevent caller destruction of active group members.
The group records the prompt version, sensitivity, size, and digest.
Each execution reads through the normal object API, preserving access checks and execution-fence read tracking.

Only a group currently running can dispatch its selected child.
The [runtime hook](../../kernel/core/exec/runtime.c) executes that child's private model image and verifies its exact output before accepting the result.
Direct execution, changed task types, external-call descriptors, widened flags, or changed prompt declarations cannot bypass the group scope.
An accepted result remains private until the whole group's completion rule passes.

| Group semantics | Completion | Failure and cancellation |
| --- | --- | --- |
| Required | Every branch must pass its expected-output check. | Failure stops the group; unstarted required branches remain pending until explicit abort or removal. |
| Trial | The first passing branch becomes the winner. | A failed output check permits the next trial; success or budget exhaustion cancels unstarted trials. |

The group charges each candidate's full token ceiling before attempting it.
Those conservative charges include failed attempts and cannot exceed the group budget.
Required groups need enough budget for every candidate's ceiling at creation.
A completed trial group exposes only its winner's output; a completed required group exposes every accepted output.
Failed groups expose no result through the read API.

Result reads recheck the prompt's current version, digest, sensitivity, and owner access.
A stale source or revoked read permission prevents result retrieval.
The owner or controller can run, inspect, read, or abort a group.
Creation and removal remain controller operations; foreign Cells cannot control or read the group.

Registered branch identities cannot authorize [protected effects](../../kernel/core/cap/effect.c), ordinary external dispatch, or staged-state commits.
That restriction survives changes to a public side-effect flag.
Unstarted trial cancellation changes only those pure leaf Cells and removes their queue entries.
It leaves the shared parent execution fence running.

## Native checks

The [regression](../../kernel/core/tools/research_day062.c) first runs three competing model candidates under an eight-token budget.
The first produces an invalid result; the second produces the expected `BBBB`; the third is cancelled before execution.
The group records two attempts, one accepted winner, one cancellation, and eight charged tokens.
The parent fence remains active, and the cancelled branch leaves its queue.

Required-group checks accept both `AAAA` and `BBBB` when both branches pass.
A failed required group hides its partial result and preserves the unstarted branch until explicit abort.
A six-token trial budget stops after one four-token failed attempt because another full attempt cannot fit.

Other checks cover copied-specification changes, source corruption, and read permissions for both the parent and child.
They also cover stale epochs, short output buffers, malformed counts, insufficient budgets, parent cognitive limits, and failed construction returning child slots.
A changed branch descriptor cannot invoke an external provider.
Protected-operation preparation and staged commit remain denied even after the fixture enables the public side-effect flag.

A foreign Cell fails to inspect or operate the group.
The actual parent then runs a fresh group inside its own execution, reads the winner, and completes.
The fixture removes the groups and verifies that their child Cells and retained references are released.

## Limits

The native runtime executes branches sequentially.
This step establishes completion and cancellation semantics without claiming parallel acceleration, scheduling fairness, or latency improvements.
The shared prompt is an immutable object reference; no copy-on-write KV cache or branch memory delta is implemented.

Candidates use the toy model's bounded adapter format and deterministic generation.
Their acceptance checks compare exact bytes against controller-supplied expectations.
Those checks are suitable for the native regression and do not establish reasoning quality on open-ended tasks.

Effects are prohibited for these pure branches; the API does not buffer external transactions for later winner commit.
Results are private boot-local byte buffers, while existing Cell traces record execution outcomes.
No durable group checkpoint, semantic result aggregation, dynamic graph rewriting, or arbitrary tool speculation is added.
This step does not reproduce the briefing's model-training, throughput, hardware, or quality measurements.
