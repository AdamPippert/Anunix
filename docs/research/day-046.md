# Day 046: Bind policy candidates to executed validation

The August 10 briefing separates model proposals from a deterministic controller that builds, tests, and accepts policy changes.
Anunix already checks bounded routing proposals, measured constraints, and private evaluation receipts.
The comparison baseline, `c67f82f`, lacks a gate that connects source contents to both booted artifacts and their complete regression records.

## Scope

The source is [Day 046 in the daily review](daily-review.md#day-046--2026-08-10).
The source message identifier is `e0ca45f5-7a92-4443-8448-b8cd685e712d`.
This step implements the build and functional-validation boundary for source candidates.
The native Anunix kernel remains the execution target.
The briefing's Linux scheduler experiments and reported performance gains remain untested.

## Implementation

The [source tool](../../tools/source_identity.py) hashes sorted relative paths and file contents with explicit lengths.
The input set includes the Makefile, the generator, and kernel files with `.c`, `.h`, `.S`, `.ld`, or `.inc` suffixes.
The input set includes all kernel architectures; a change outside the selected architecture also changes the fingerprint.
The tool rejects missing required inputs and symbolic links within the selected files.

The [Makefile](../../Makefile) generates the header before native compilation.
Unchanged contents preserve the header's modification time.
A changed fingerprint makes every kernel object depend on the new header, including changes to included headers.
The [kernel profile](../../kernel/core/tools/kernel_profile.c) exposes the immutable fingerprint through `sysinfo`.
The existing architecture and instrumentation descriptor retains its schema and behavior.

The [VM runner](../../tools/research_vm.py) requires consistent source markers within each artifact before boot.
The runner compares the guest marker with the artifact marker and rechecks artifact identity after the regressions.
The result records the boot mode, source fingerprint, compiled configuration, artifact digest, and individual test outputs.
Host and conformance runs also emit the source fingerprint after their checks succeed.

The [candidate gate](../../tools/candidate_gate.py) requires the source tree, kernel, image, both VM reports, host log, and conformance log.
The caller supplies the declared revision and final required day.
The gate requires every day through that boundary, followed by a repeat of the final day, in both boot modes.
Every result needs an exact passing marker; a passing Boolean cannot override contradictory guest output.

The gate compares the current source fingerprint with both artifacts, guest outputs, and host records.
The gate also checks artifact digests, sizes, revision declarations, expected boot modes, and successful profile checks.
Missing, failed, substituted, duplicated, or incomplete evidence prevents record creation.
The gate creates a new JSON record only after every check passes; an existing record cannot be overwritten.

The record contains the source fingerprint, declared revision, required regressions, artifact identities, and evidence digests.
The record does not activate a policy or grant publication authority.
The [publication gates](publication.md) still control final GitHub integration.

The [native regression](../../kernel/core/tools/research_day046.c) requires a complete, nonzero source marker in the running kernel.
The [host regressions](../../tests/test_candidate_gate.py) cover source drift, image changes, wrong identities, missing tests, contradictory outcomes, and absent evidence.

## Limits

The source fingerprint covers the explicit input set, not every build dependency.
Bootloader sources, binary assets, host test definitions, toolchain binaries, environment settings, and arbitrary compiler overrides remain outside that fingerprint.
Artifact digests still identify the complete kernel and disk image used by the lab.
The declared revision remains a caller assertion; the fingerprint independently checks the selected source contents.

The gate assumes trusted workers and stable files during validation.
Unsigned records and caller-supplied logs do not prevent forgery by a malicious worker or controller.
The JSON record describes a completed validation; later consumers must recheck identities before using changed files.
The caller must select the complete required day range; final release preparation checks the current research queue.

These checks establish functional regression results, not performance improvement or statistical significance.
The gate does not synthesize policies, install Linux schedulers, sign artifacts, or replace Anunix's runtime promotion checks.
