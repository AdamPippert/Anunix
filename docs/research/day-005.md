# Day 005: Evidence in an optimization workflow

The June 30 briefing packages observation, evaluation, promotion, and rollback as auditable workflows.
Anunix already provides workflow graphs, State Objects, and the promotion gate checked on Day 004.
The baseline workflow executor has no step that consumes evidence and requests a gated installation.

## Implementation

The new `cap_promotion` workflow node consumes a sealed evidence object on input port 0.
The node emits its decision object on output port 1.
The workflow policy denies capability installation by default.
A trusted kernel caller must explicitly enable `allow_capability_install` for that workflow.
Workflow bundles carry no such authority.

The evidence record names the candidate, incumbent, candidate count, and paired scores.
The [record definitions](../../kernel/include/anx/promotion_evidence.h) specify the schema identifiers and native structures.
The evidence's incumbent must match the candidate's declared incumbent.
The Day 004 gate then checks the installed incumbent and comparison margin.

The kernel reserves a complete decision record before it attempts installation.
The record retains the supplied evidence, source identifier, and operation result.
Its provenance names the source evidence object as its parent.
The kernel seals the record after the attempt.
The workflow trace references that decision even when the gate rejects the candidate.

The regression runs a three-node workflow: evidence reference, promotion, and output.
The workflow rejects missing authority and unsealed evidence.
A tied trial suspends the workflow and leaves the incumbent installed.
Evidence that names the wrong incumbent produces a recorded rejection.
A later run with qualifying evidence installs the candidate and returns the decision object.

## Limits

Sealing preserves supplied measurements; it does not authenticate their producer or prove benchmark quality.
The gate still uses the existing deterministic margin rule.
Successful installation adds a candidate engine; it does not replace the active routing policy atomically.
The decision record and installation do not form a crash-durable transaction.
Automatic profiling, benchmark generation, signatures, and policy rollback remain separate work.
The test retains evidence, decisions, and retired capability records in the guest store.
