# Day 055: Enforce flow policy and retain ambiguous outcomes

The August 19 briefing separates operation authority, information flow, resource admission, and evidence of what happened.
A tool permission must not authorize confidential egress, and a timeout must not become an automatic retry.
Anunix already has protected-effect primitives, but the comparison baseline, `6e063b6`, bypasses the accumulated sensitivity check during direct external dispatch.

## Scope

The source is [Day 055 in the daily review](daily-review.md#day-055--2026-08-19).
The source message identifier is `86cfdecb-bae0-4623-9998-6f19c1f1247a`.
This step strengthens the existing external boundary and adds an explicit protected-operation path through registered providers.

## Implementation

The [external dispatcher](../../kernel/core/exec/external.c) now checks the executing Cell's run-level sensitivity before an ordinary provider call.
An unbound destination cannot receive information from a fenced run whose accumulated read label exceeds public sensitivity.
Existing contract, identity, run-state, and tool-namespace checks remain independent prerequisites.
Unscoped controller calls retain their existing administrative behavior.

The [protected-operation API](../../kernel/include/anx/external_operation.h) provides a destination-bound path for approved transfers.
Only a controller can prepare an operation for an existing Cell.
Preparation copies the endpoint, method, tool handle, and up to 4,096 request bytes into private storage.
A data-bearing operation requires a registered Sink selected by the controller.
Optional source binding records its object identifier, version, and content hash after checking the owner's read permission.

Preparation checks the contract, tool namespace, effect authority, and destination sensitivity before allocating an opaque operation identifier.
The registry holds at most 32 records and retains a reference to an owner whose operation remains prepared.
The record also binds the provider's function, context, and registration generation.
Changes to the caller's original request cannot redirect the prepared operation.

Only the executing owner can dispatch its prepared operation.
Dispatch repeats contract, namespace, source, Sink, and effect checks before invoking the actual registered provider.
A changed source version or provider registration leaves the operation prepared and returns `ANX_EBUSY`.
Revoked destination permission leaves it prepared and returns `ANX_EPERM`.

The manager records `DISPATCHING` before entering the provider and releases its registry lock during execution.
A reentrant dispatch sees that state and fails.
A completed provider call returning `ANX_OK` records `COMMITTED`, including the provider's application status code.
Any negative provider result or oversized response records `UNKNOWN` because execution may already have occurred.
Neither outcome permits another dispatch with the same operation identifier.

Outcome records retain the owner identity, request digest, source identity, Sink name, phase, and transport result.
Owner references are released after settlement, so retained unknown outcomes do not keep completed Cells alive.
Controllers may discard prepared or committed records; unknown records remain available for inspection and reject discard.
Identifiers never repeat within the current boot.

## Native checks

The [regression](../../kernel/core/tools/research_day055.c) first reads a confidential object inside a fenced Cell.
An ordinary nested provider call is denied even though the Cell has call authority.
The protected path then demonstrates an approved confidential transfer through a registered Sink.

Five protected-operation cases exercise success, an ambiguous timeout, a changed source, revoked Sink permission, and replaced provider registration.
The actual provider verifies that it received the copied original request and cannot dispatch its own in-flight operation again.
A timeout remains `UNKNOWN`, repeated dispatch fails, and controller discard is rejected.
A foreign Cell cannot inspect or dispatch the operation, while controller dispatch is also rejected outside the executing owner.
Cleanup confirms that terminal operation records release their Cell references.

## Limits

Protected outcome tracking requires the explicit operation API; legacy direct calls receive the stronger flow check but do not acquire these operation records.
Accumulated read labels depend on existing run-fence bindings and instrumented State Object reads.
The controller remains responsible for binding the correct Sink to the destination and selecting complete source dependencies.
The implementation binds one optional source object, without proving that it describes every byte in the request.

The provider callback remains trusted kernel code.
`COMMITTED` means the provider returned a completed response; its application status can still describe a rejected business operation.
The API does not certify that an error occurred before execution, restore authority, or reconcile unknown outcomes automatically.
A deliberately new operation identifier represents new work; callers must preserve the original identifier when considering a retry.

Records and copied payloads exist only in the current boot's private registry.
There is no durable journal, restart recovery, release-approval token, or cross-provider transaction.
Unknown outcomes retain their slots until reboot, and a full registry rejects further preparation.
Request-size and registry limits bound this prototype; end-to-end overhead and broader scheduling budgets remain unmeasured.
