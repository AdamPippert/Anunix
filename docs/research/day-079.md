# Day 079: Commit resource decisions against current observations

The September 12 briefing makes phase identity, partial progress, and state versions inputs to scheduling decisions.
The source message is `01591a3b-c89f-42b3-bdfb-2c93786e2f23` in the [research conversation](https://chatgpt.com/c/6a3eabf4-cb88-83ea-942e-a601dd12b392).
Its central rule separates a planner's proposal from the deterministic validation required before commit.
The Anunix experiment applies that rule to a bounded change in replica count.

## Comparison

| Area | Existing Anunix | Day 079 change |
| --- | --- | --- |
| Logical progress | Physical plans capture the graph epoch | Resource proposals capture progress and the logical program digest |
| Phase | Phase changes advance their epoch | The proposal captures the phase, lease identity, and reserved capacity |
| Resource shape | Resize checks the supplied shape epoch | Commit also checks materialized replicas and the observed memory geometry |
| Authority | Individual operations check their current owner and source | A proposal binds the identity record and run-fence generation across planning |

The [resource-decision API](../../kernel/include/anx/resource_decision.h) adds an issued proposal identity and lifecycle.
The [controller](../../kernel/core/route/resource_decision.c) composes the existing graph, phase, shape, identity, and fence checks.
The [resource-shape implementation](day-074.md) remains responsible for the actual resize.

## Implementation

The controller proposes a replica count from one through four for an existing logical graph and resource shape.
Both objects must belong to the same live owner.
The current inference phase must cover the requested replica capacity.
The registry holds at most 16 proposals and retains each owner's Cell.

The proposal privately captures these observations:

- Logical identity, epoch, program digest, completion mask, state, and operation counts.
- Phase epoch, role, memory tier, lease identity, and reserved capacity.
- Shape epoch, replica count, resident replicas, physical pages, bytes, geometry, and source snapshot.
- The owner's ancestry, admitted identity record, bound run fence, and fence generation.

Commit accepts an issued proposal identifier, not replacement observations from the caller.
The controller rechecks live scope, contract, scheduling domain, identity, fence, phase capacity, model data, and read access.
It then compares the current observations against the private proposal before invoking resize.
No planner, model inference, or external callback runs inside that validation boundary.
The current bootstrap-CPU implementation retains interrupt exclusion from observation through the resize call.

Success records the applied shape epoch and marks the proposal committed.
Revalidation failure marks the proposal stale and records its error.
A stale or committed proposal cannot execute again; the controller must issue a new proposal.
Validation rejection leaves the resource shape and caller output unchanged.
The proposal retains its original observation for later inspection.

Only the controller can propose, commit, or destroy a decision.
The owner can inspect its issued records; foreign Cells cannot inspect them.
Copied fields do not change the private target count or observed versions.
Dependent graphs and shapes retain their existing lifetimes, so removing one prevents later commit through its old identifier.

## Native checks

The [fixture](../../kernel/core/tools/research_day079.c) prepares a two-operation logical graph with a one-slot model cache.
The first seven proposals encounter separate changes before commit.
Every failed validation preserves the current shape and caller output and prevents reuse of the proposal.

| Change after observation | Expected rejection |
| --- | --- |
| Lazy cache materialization without a shape-epoch change | Observed resident state differs |
| Completion of the first logical operation | Progress and graph epoch differ |
| A phase resize | Phase epoch and reservation differ |
| A direct shape resize | Shape epoch and replica count differ |
| A run hold followed by release | Fence generation differs even though the run is active again |
| A changed model payload | The canonical source no longer matches |
| Revoked model read access | Current authority denies the operation |

A fresh proposal retains a target of two replicas after the caller changes its copied count to four.
Commit applies the private two-replica target and preserves the completed first result.
A fresh physical plan executes the second logical operation from that resource shape.
Actual CPU generation produces `AAAA` for both operations.
The completed mask is `3`, which represents both nodes; the physical operation count is two.

The fixture also rejects zero replicas, five replicas, and a count above the current phase capacity.
Active Cells cannot issue, commit, or remove decisions.
The exact owner can inspect the committed record, while foreign inspection fails.

## Limits

The action catalog contains only replica-count changes for the existing CPU toy-model cache.
The observed graph supplies progress context; the API does not authorize graph edits or complete unfinished operations.
Physical execution retains its separate validation of model-use requests and their prompt sources.
The proposal does not snapshot all machine state, queues, network topology, power settings, or unrelated resource domains.

The commit boundary relies on the kernel's current execution on one bootstrap CPU.
It is not a general transaction across concurrently executing processor cores or distributed machines.
Existing direct APIs retain their original contracts; they do not automatically issue these proposals.
No automatic planner, GPU power controller, partial-tensor transport, performance gain, or persistent decision store is claimed.
